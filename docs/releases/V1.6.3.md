# V1.6.3 — 采购合并与链路一致性修复

## 本版目标

采购来源与吉客云执行单据不再假设严格 1:1。支持真实业务场景：

- 多张 1688 / 淘宝 / 拼多多 / 其他渠道采购订单，共同对应 1 张吉客云采购单；
- 一张线上采购订单仍可拆到多张吉客云采购单（沿用既有 split 关系）；
- 原始采购订单不合并、不删除，只新增可审计的业务关系；
- “完成”从“有单据即可”升级为金额、数量、付款、发票、认证全部闭环。

## 1. 采购合并

新增「采购合并」入口：

- 系统只做高置信推荐，不自动合并；
- 推荐条件：供应商一致、45 天时间窗、2~4 张来源订单金额合计命中吉客云采购单；
- 支持手工勾选多张来源订单并填写每单分摊金额；
- 合并采用原子保存：任意金额不平，整组拒绝，不留下半组关联；
- 吉客云采购单金额必须等于来源订单分摊金额合计；
- 每张来源订单在吉客云侧的累计分摊不得超过该订单实际采购金额。

数据仍使用既有 `jackyun_purchase_order_links`：

- `relation_kind=merged`：多张来源订单共用一张吉客云采购单；
- `alloc_amount`：该来源订单在吉客云采购单中的业务分摊金额。

## 2. 共用入库单 / 入库明细分摊

新增显式共用入库明细分摊能力：

- 同一吉客云入库明细可按数量分给同一采购合并组的多张来源订单；
- 分摊总数量绝不允许超过吉客云实际入库数量；
- 不复制采购金额，不删除吉客云入库事实；
- 现有自动反填仍保持保守排他，只有明确执行“合并采购入库分摊”时才允许共用来源明细。

## 3. 完成状态强校验

采购订单从 `inbound` 推进到 `done` 前，必须同时满足：

1. 吉客云采购单关系金额闭环；
2. 入库金额覆盖采购目标，合并/拆分场景的 SKU 均明确落到真实入库明细；
3. 发票金额覆盖采购目标；
4. 付款 / 结算金额覆盖采购目标；
5. 有效进项发票认证金额覆盖采购目标。

部分入库、部分开票、部分付款不再能够误标“完成”。API 可通过
`GET /api/v1/purchase/orders/{po_id}/closure` 查看各环节覆盖和具体卡点。

## 4. 发票与吉客云主单兼容

税务清单若明确关联的是吉客云采购单：

- 普通 1:1 采购直接映射到来源采购订单；
- 合并采购按 `alloc_amount` 比例映射到各来源订单；
- 避免税务页已经显示“已匹配”，采购工作台仍显示“待发票”。

旧的手工采购发票登记仍兼容，但只有税务台账中的有效已认证发票可满足“认证覆盖”。

## 5. 多渠道订单号隔离

`external_purchase_orders` 幂等键由单一 `external_order_id` 改为：

`platform + external_order_id`

因此 1688、淘宝、拼多多可以存在相同数字订单号而互不覆盖。同步和查询兼容层同时增加渠道约束：

- 1688 导入只更新 `platform=1688` 的工作流副本；
- 采购链列表不会把非 1688 同号订单并入 1688 文件副本；
- 税务清单只提供订单号且命中多个采购渠道时，进入人工确认，不自动猜测。

迁移只调整唯一约束，不删除、不改写现有业务记录。

## 6. API / 操作一致性

新增：

- `GET /api/v1/purchase/merge-suggestions`
- `POST /api/v1/purchase/merge-groups`
- `GET /api/v1/purchase/jackyun-groups/{jackyun_po_id}`
- `GET /api/v1/purchase/orders/{po_id}/closure`
- `POST /api/v1/purchase/inbound-split`
- `DELETE /api/v1/purchase/orders/{po_id}/allocations/{item_id}`（规范 SKU 删除路径）

旧 SKU 删除路径继续保留，避免历史页面/脚本立刻失效。

## 安全原则

- 不删除线上原始采购订单；
- 不删除吉客云采购单、入库单、结算单；
- 合并只创建关系；
- 金额、数量不闭环时拒绝推进；
- 所有关键合并/分摊动作写审计日志；
- 数据库迁移不做破坏性清洗；
- 保持单端口 8000 部署结构不变。
